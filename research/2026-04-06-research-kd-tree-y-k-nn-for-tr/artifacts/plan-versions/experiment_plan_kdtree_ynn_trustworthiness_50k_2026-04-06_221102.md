# Experiment Plan: KD-tree Y k-NN for trustworthiness() at n ≥ 50K

## Motivation

`trustworthiness()` is the primary quality metric used to validate spectral
initialization fidelity. Its current Y k-NN implementation is O(n²) — a flat
distance fill plus `select_nth_unstable_by` — which extrapolates to ~3.6s at
n=50K and ~14.5s at n=100K even with the AVX2 batch kernel (PR #237). At
UMAP output dimensionality d_y=2, KD-trees achieve maximum pruning efficiency:
O(k log n) per query vs O(n) brute-force. The prior scope
(`research/2026-04-06-y-heap-bottleneck-optimization/`) flagged this as H3
(n≥50K follow-up) without implementing it.

This experiment answers two questions: (1) Does `kiddo` v5
`ImmutableKdTree<f64, u32, 2, 32>` yield the predicted ≥5× speedup at n=50K?
(2) At what crossover n does the KD-tree build cost amortize and the path
becomes worth enabling? Results directly inform whether to ship an adaptive
`kdtree` feature flag in `trustworthiness()`.

---

## Hypothesis

**Null hypothesis (H0):** Replacing the brute-force Y k-NN block with
`ImmutableKdTree` yields ≤1.5× wall-time speedup at n=50K (i.e., no meaningful
gain despite algorithmic complexity reduction).

**Alternative hypothesis (H1):** Building `ImmutableKdTree<f64, u32, 2, 32>`
once per `trustworthiness()` call and querying it in the Rayon parallel loop
reduces Y k-NN from O(n²) to O(n k log n), yielding ≥5× wall-time speedup at
n=50K and ≥10× at n=100K relative to `flat_simd`, while preserving
`|T_kdtree − T_brute_force| < 1e-12` on all tested inputs.

### Phase 5: KD-tree Implementation in `src/metrics.rs`

Add a KD-tree branch in `trustworthiness()`, gated on both `#[cfg(feature = "kdtree")]` and a runtime `d_y == 2` check. The branch executes when `feature = "kdtree"` is enabled and `d_y == 2`:

```
const N_KDTREE_THRESHOLD: usize = 0;  // Set to 0 for experiment (forces kdtree at all n)
```

Before the `(0..n).into_par_iter()` loop:
1. Build the Y flat slice: `y_flat_2d: Vec<[f64; 2]>` from `y` rows, with index stored as `u32`
2. Time the build: `let t_build = Instant::now()`
3. `let tree = Arc::new(ImmutableKdTree::<f64, u32, 2, 32>::new_from_slice(&y_flat_2d));`
4. `Y_KDTREE_BUILD_NS.fetch_add(t_build.elapsed().as_nanos() as u64, Ordering::Relaxed)`

Inside the Rayon loop, replacing the `COMB_DIST_Y.with(...)` block:
1. `let results = tree.nearest_n::<SquaredEuclidean>(&[y_i[0], y_i[1]], NonZero::new(k+1).unwrap())`
2. Filter `results` to drop the entry with `item == i as u32` (self)
3. Collect the remaining `k` items' indices into a stack-local array `knn_y: [u32; K_MAX]` or `SmallVec`
4. Proceed directly to the penalty loop (unchanged)

Self-exclusion: kiddo returns exact k+1 results sorted by distance; `dist==0` entry has `item == i as u32`. After dropping it, the remaining k entries are the true k-NN.

Thread safety: `ImmutableKdTree<f64, u32, 2, 32>: Sync + Send` per kiddo docs; wrapping in `Arc` is sufficient for sharing across Rayon threads.

## Analysis Plan

For each n in {1K, 5K, 10K, 50K, 100K}:

1. **Speedup ratio:** `flat_simd_total_ms / kdtree_total_ms` — primary test of H1
2. **Build amortization:** `kdtree_build_ms / (flat_simd_total_ms - kdtree_query_ms)` — fraction of savings consumed by build; < 0.5 confirms H4
3. **Crossover identification:** The n at which `kdtree_total_ms < flat_simd_total_ms` first holds — determines adaptive dispatch threshold (H2)
4. **Correctness delta:** All `t_tw_11` assertions at `|ΔT| < 1e-12` — confirms H3 (tie-breaking benign)

**Expected pattern:** speedup < 1× at n=1K (tree overhead dominates), approaches 1× at some n=T_cross ∈ [5K, 15K], then ≥5× at n=50K, ≥10× at n=100K. If the actual crossover is higher than 15K or speedup at 50K < 5×, H0 is not refuted.

**Statistical treatment:** Criterion reports `mean ± std` over 10 samples. Report both. Speedup is computed from means; uncertainty propagation is `sqrt((σ_flat/μ_flat)² + (σ_kd/μ_kd)²) * speedup`. If coefficient of variation exceeds 10% on any measurement, flag it in the report and note possible thermal throttling or OS interference.

## Success Criteria

- **Conclusive positive (ship kdtree feature):** KD-tree speedup ≥ 5× at n=50K AND ≥ 10× at n=100K AND all `t_tw_11` assertions pass (`|ΔT| < 1e-12`). Crossover n identified with ≤ 2× variance across repeated runs. Build cost ≤ 25% of total savings at n=50K.
- **Conclusive negative (do not ship):** KD-tree speedup < 2× at n=50K after correct implementation confirmed by profiling step-level breakdown.
- **Inconclusive:** Speedup is 2×–5× at n=50K, OR correctness failures occur at `|ΔT| ≥ 1e-12` (requiring investigation of tie-breaking semantics), OR benchmark variance > 20% across samples (suggesting measurement interference).

## Threats to Validity

### Internal

- **Thermal throttling:** n=100K Criterion runs are long (~10–30s per sample × 10 samples). If the host thermal-throttles mid-run, later samples will be slower than earlier ones, artificially inflating wall time for both paths equally but potentially masking speedup differences. Mitigation: inspect Criterion's per-sample scatter plot; flag if std/mean > 0.15.
- **Rayon thread pool saturation:** Both brute-force and KD-tree paths use `(0..n).into_par_iter()`. At n=50K the Rayon parallel overhead is negligible relative to compute. But if `RAYON_NUM_THREADS` is set to a non-default value in the environment, results will not match published kiddo benchmarks. Mitigation: record thread count in the report; run with unset `RAYON_NUM_THREADS`.
- **kiddo query scratch allocator:** kiddo v5 `ImmutableKdTree::nearest_n` uses a heap-allocated priority queue internally per query. If the priority queue allocates on every call, the per-row heap allocation pressure could dominate at high n and mask the true algorithmic gain. Mitigation: profiler step breakdown isolates `y_dist` (query) from overall wall time; if query time is unexpectedly high at n=100K, compare to kiddo's own benchmark numbers.
- **Tie-breaking at exactly-equidistant neighbors:** The current brute-force sorts `(dist, index)` lexicographically, kiddo does not guarantee index-based tie-breaking. In practice, uniform random float64 data has collision probability ≈ 2^{-52} per pair, making this measure-zero. But the correctness test `t_tw_11` must cover at least one degenerate case (repeated Y coordinates) to rule out systematic differences. **Add one subtest with duplicate Y rows.**

### External

- **d_y = 2 restriction:** The KD-tree path is restricted to `d_y == 2` (kiddo const-generics require compile-time K). If future UMAP variants produce d_y = 3 embeddings, this optimization does not apply. Generalization to d_y ∈ {2,3} via a match arm is straightforward but out of scope.
- **Non-Rayon environments:** Speedup numbers are measured with Rayon parallel queries. Single-threaded `trustworthiness()` calls would show lower absolute speedup (tree build overhead is non-parallelizable) but similar ratio since both paths scale linearly with Rayon threads.
- **Hardware specificity:** kiddo v5 uses SIMD-accelerated distance computations internally. With `target-cpu=native`, results reflect the host ISA (AVX2/AVX-512). On hardware without AVX2, kiddo's scalar fallback may underperform the `dist_sq_2d_avx2_batch` kernel even at large n. Results should be reported with host CPU model.
- **Uniform random data:** UMAP 2D embeddings have spatial clustering structure that real k-NN queries exploit more efficiently (prune more branches) than uniform random. Benchmark on uniform random data gives a conservative (pessimistic) estimate of KD-tree speedup on real embeddings.
